Azure IoT C Library — Developer Experience Comparison
Scenario: DPS X.509 Provisioning + Telemetry Send (1:1 comparison)
Scope: Both samples perform the same end-to-end flow — provision a device via DPS using X.509 certificates, connect to the assigned IoT Hub, send telemetry, and disconnect. The new-library excerpt shows the Classic az_iot_mqttv3_telemetry_client; an MQTT v5 assignment selects az_iot_mqttv5_telemetry_client after CONNECTED while keeping the same message and callback types. The original C SDK requires combining two separate samples (prov_dev_client_ll_x509_sample + iothub_ll_telemetry_sample) to achieve this; the new library does it in a single file.
1. New Library — Complete Sample (Annotated)
Source: the former Classic-only telemetry sample, since replaced by samples/unified/telemetry/main.c (which also serves AEG hubs and device moves) — ~95 lines of functional code (excluding comments, blank lines, and logging)

az_iot_certificate_provider_pem certs; // X.509 cert provider az_iot_connection_client connection_client; // DPS + Hub connection az_iot_mqttv3_telemetry_client telemetry_client; // Classic telemetry sender } sample_state_t; // ─── Callbacks (simple, typed) ─────────────────────────────── static void on_conn_state(const az_iot_connection_state_event* event, void* ctx) { // Just store the new state — 3 lines total ((user_context_t*)ctx)->conn_state = event->state; } static void on_send_done(az_iot_result status, void* ctx) { // Delivery confirmation — 2 lines ((user_context_t*)ctx)->send_status = status; ((user_context_t*)ctx)->send_done = 1; } int main(void) { // ─── Step 1: X.509 Certificate provider ────────────────── // One struct with three file paths — no #ifdef, no embedded PEM blobs az_iot_certificate_provider_pem_options pem = az_iot_certificate_provider_pem_options_default(); pem.trusted_ca_pem_path = config.ca; pem.client_cert_pem_path = config.cert; pem.client_key_pem_path = config.key; az_iot_certificate_provider_pem_init(&certs, &pem); // ─── Step 2: Connection client (DPS is automatic) ──────── // When id_scope is provided, DPS provisioning // happens internally during open() — no separate API needed az_iot_connection_client_options copts = az_iot_connection_client_options_default(); copts.dps.id_scope = id_scope; copts.dps.registration_id = reg_id; copts.certificate_provider = &certs.base; az_iot_connection_client_init(&conn, &copts); az_iot_connection_client_add_state_observer(&conn, on_conn_state, &ctx); // ─── Step 3: Plug in MQTT transport (one line) ─────────── az_iot_connection_client_register_mqtt_factory( &conn, az_iot_paho_factory_create_v3_1_1()); // ─── Step 4: Open (provisions via DPS → connects to Hub) ─ az_iot_connection_client_open(&conn); while (ctx.conn_state != AZ_IOT_CONN_STATE_CONNECTED) az_iot_connection_client_do_work(&conn, 50); // ─── Step 5: Select the feature client from the profile ── az_iot_mqttv3_telemetry_client_init(&telemetry, &conn); while (!ctx.send_done) az_iot_connection_client_do_work(&conn, 50); // ─── Step 7: Close & cleanup ───────────────────────────── az_iot_connection_client_close(&conn); sample_state_destroy(&state); // deterministic, single call }

Key Takeaways (Developer Experience Focus)
  • 2× less code for the same end-to-end scenario (~95 vs ~200 functional lines).
  • Single mental model: one connection client handles DPS + Hub; no need to stitch two disjoint APIs together.
  • Zero #ifdef in application code — choices (protocol, cert format) are made through typed structs and adapters, not preprocessor macros.
  • No manual memory management in the message send path — messages are stack structs, not heap-allocated handles the caller must destroy.
  • Fewer concepts to learn: 4 core types vs 8+ types/APIs spread across two separate client libraries.
  • Minimal dependency tree: 2 dependencies vs 13 git submodules that the original C SDK must clone, build, and maintain.
